# Agent 开发团队（agent-dev-team）

你打开的对话默认是「负责人」：只想、只调度，不写代码。读代码交给便宜的子代理，验收交给脚本，逐行审代码交给 Codex。改动大（超过约 200 行或 5 个文件）时，验收通过后、审核前先派一个 dev-sonnet 用 qingli 技能（插件自带，改编自 ponytail，MIT，作者 Dietrich Gebert）清理代码：找出多余的直接删，删完跑测试，清理完重新验收。合并前必须审核通过，做完按你的 Slack 汇报规则汇报，一批做完再整理记忆。

负责人向你提问一律用提问器（AskUserQuestion 工具），不在正文里问。你给的是问题或目标时，它先问一轮（最多 3–4 题：为什么要做、谁在用、做成什么样算成功）；你给的是具体改法就直接做，它有更好的办法只提一句让你选。一个需求最多问一轮。

验收比以前严：任务分支改了已有测试的断言、删了已有测试文件、给已有测试加了跳过标记，验收直接「不通过」（派活单明确允许时才放行）。修 bug 的任务要先写一个会失败的测试再修。只有改了页面的任务才做浏览器截图对照。一批任务合并后，会另写一页任务说明（用 answer-me-with-html 技能，排成 HTML 后发布成私有页面，链接贴进汇总和任务卡；没装这个技能就跳过）；PPT 只在你点名时做。

## 安装

首选从市场安装：

1. 在 claude.ai 或 Claude 桌面版：Customize → Plugins → Add → Add marketplace，选这个仓库（`srmming/agent-dev-team`）。
2. 装 `agent-dev-team`。需要状态栏，再装 `agent-dev-team-status`。
3. 之后可以打开「自动同步」，或者手动点「检查更新」。只有改了 `plugin.json` 里的版本号，才会收到更新。

命令行里的写法：`/plugin marketplace add srmming/agent-dev-team`，再 `/plugin install agent-dev-team --marketplace srmming/agent-dev-team`。

私有仓库也能用，在 claude.ai 上要先授权 Claude 的 GitHub 应用读这个仓库。

以前手动上传过 zip 的：装好市场版后，把上传的那份删掉。同名时市场版优先，上传的那份会显示未加载。

备用方式：把仓库打成 zip 手动上传，或者用 `claude --plugin-dir /path/to/agent-dev-team` 只在这一次打开的 Claude Code 里加载。

## 状态栏（可选）

仓库的 `statusbar/` 目录是一个配套小插件 agent-dev-team-status：在输入框上方显示当前模式和在跑的子代理，可以点按钮切换「负责人模式 / 普通对话」「全自动 / 半自动」。它和主插件读写同一个对话状态文件。

它要单独安装，装法见 `statusbar/README.md`。没装时直接发口令切换：「负责人模式」「普通对话」「全自动」「半自动」。

状态栏目前只在测试里跑过，还没在真实的桌面版里确认过显示和点击。

## 角色怎么认

按顺序判断：

1. 守卫关了（见「开关」）：不管。
2. 这个对话标成了「普通对话」：普通对话。普通对话里开的后台子代理也按普通对话放行。
3. 后台子代理（钩子输入里有 `agent_id`）：子代理。
4. 这个对话记过别的角色：用记下的角色。
5. 当前分支以 `kuaixiu/` 开头：对接窗口（旧做法，保留兼容）。
6. 其余：负责人。不在 git 仓库里也一样。

每个对话的角色存在 `~/.claude/agent-dev-team/sessions/<对话 id>.json`，例如 `{"role": "lead", "auto": "full"}`。环境变量 `AGENT_DEV_TEAM_HOME` 可以换这个目录。

## 怎么切换

点状态栏按钮，或者直接发下面这些话（整条消息就是这几个字）：

| 你说 | 结果 |
|---|---|
| 普通对话 | 这个窗口变回普通对话，可以直接改文件 |
| 负责人模式 | 切回负责人 |
| 全自动 | 审核通过后直接合并、推送 |
| 半自动 | 推任务分支、开 PR，等你点合并 |

切换后 AI 用一句话告诉你切好了。切到「负责人模式」「普通对话」时，钩子还会把这个角色的提示一起交给 AI。点状态栏按钮只改状态文件，AI 当时不知道；你发下一条消息时，钩子发现角色或模式和上次告诉 AI 的不一样，就把现在的角色提示交给 AI（没变就什么都不加）。上次告诉 AI 的是什么，记在对话状态文件旁边的 `<session_id>.told` 里。

另外两种由负责人自动使用：消息以 `【派活单】` 开头，窗口变成子代理（附上子代理守则）；以 `【快修】` 开头，窗口变成对接窗口。

## 五个脚本

都在插件的 `hooks/scripts/` 下，用 `python3` 跑，都支持 `--help`，第一行就是结论。负责人看到的绝对路径在会话开始的提示里。参数写错时退出码 2。

| 脚本 | 用法 | 第一行 | 退出码 |
|---|---|---|---|
| verify.py | `--branch <分支> [--base <基准>] [--cwd <工作副本>] [--allow <通配符>]... [--allow-test-change] [--cmd "<命令>"]... [--timeout <秒>]` | 验收：通过 / 不通过 / 出错 | 0 / 1 / 2 |
| review.py | `--branch <分支> [--base <基准>] [--cwd <仓库>] [--full] [--since <提交> --last-issues <文件>]` | 审核：通过 / 没有改动 / 不通过（第 N 轮）/ 出错（不计入失败轮数） | 0 / 0 / 1 / 2 |
| deploy_check.py | `[--cwd <仓库>] [--sha <提交>] [--wait <秒>] [--interval <秒>] [--retries <次>] [--max-poll <秒>]` | 上线检查：通过 / 不通过 / 无法判断 | 0 / 1 / 3 |
| rollback.py | `--commits <提交号>... [--cwd <仓库>] [--push]` | 回滚：完成 / 失败 | 0 / 1 |
| mode.py | `get --session <id> [--cwd <项目>]`；`set --session <id> [--role lead\|normal\|subagent\|kuaixiu] [--auto full\|semi] [--status "<文字>"] [--pool <N>]` | 打印这个对话的状态（JSON） | 0，参数不对 2 |

- verify.py：查 `<基准>...<分支>` 改了的文件有没有超出 `--allow`（不给就不查；改名时新旧路径都算）；还查已有测试有没有被动手脚：改了断言、删了测试文件、加了跳过标记，直接判「不通过」，只有派活单明确允许（例如需求就是改变已有行为）时才加 `--allow-test-change` 放行，并要在完成标准里写明；再按顺序跑 `--cmd`。命令在 `--cwd` 当前的代码上跑，所以给了 `--cmd` 时先查 `--cwd` 的 HEAD 是不是正好是 `--branch` 的顶端、有没有没提交的改动（包括没加进去的新文件），不对就不跑命令，直接判「不通过」。第一条失败（退出码非 0 或超时，默认每条 900 秒）就停，打印输出的最后 30 行。基准默认是主分支。
- review.py：开跑前先把基准和分支固定成提交号，Codex 审的就是这两个提交号之间的改动；审核期间分支上再加的提交不算。超时 1800 秒。结论只认整行就是 `VERDICT: PASS` 或 `VERDICT: FAIL` 的行（首尾可以有空白；加粗、引用、行里还有别的字都不算），取最后一个，没有结论按不通过。通过时记一个「审核单元」（见下面「审核记录」），清掉失败轮数；不通过时轮数加 1，打印问题清单（最多 60 行），第 2 轮起提醒负责人自己读一次 diff。分支有提交但合起来没改文件（空提交、改了又改回来；直接比分叉点和分支顶端的文件树，不看 diff 的输出）时不调 Codex，打印「审核：没有改动」，同样记一个审核单元。不是仓库、找不到分支、git 查不出改动、找不到审核命令、审核命令退出码不是 0、超时都算出错，不计入轮数。
  - 审核标准（写在给 Codex 的提示词里）：负责人和子代理都是配合的 AI，守卫防手误、不防刻意绕过。「严重」只算按 README 和技能教的用法或常见的普通写法、正常使用就会碰到，并且会导致结果错误、丢数据、没审过的代码进了主分支或上线、该回滚时不回滚、流程卡死的问题；要刻意构造的命令或环境才会触发的（多层嵌套引号、符号链接拼路径、少见的 git 配置组合、别名等）算「一般」，照样列出来但不挡合并。有严重问题才不通过。
  - 增量复审：不通过、并且 Codex 给出了有效的 `VERDICT: FAIL` 时，把这次的起点、顶端和 Codex 的输出全文存进 `last-<分支>.json`；没有有效结论（空输出、没有结论行）时照旧按不通过计一轮，但不动原来的记录。下次审同一分支时，如果起点没变、上一轮的顶端是现在顶端的祖先，就只复审增量：让 Codex 逐条确认上一轮的问题修好没有，再审「上一轮的顶端..现在的顶端」有没有新的严重问题（上一轮的严重问题没修好也算不通过），输出第二行写「增量复审」。增量通过 = 前面全量审过、问题都修了、这次的改动没有新的严重问题，记的审核单元和全量通过一样（起点到顶端整段），守卫照常认。通过后清掉这条记录和失败轮数。`--full` 强制全量；rebase 过（起点变了）、没有记录、上一轮的顶端不在现在的历史里、上一轮的问题清单超过 2 万字（不截断，免得开头的问题丢掉）时自动全量，除了没有记录，输出里都会说明原因。上一轮没存记录（旧版脚本跑的）时，用 `--since <上一轮审到的提交> --last-issues <问题清单文件>` 手动指定。
- deploy_check.py：推送后检查线上。项目配置有 `deploy_check.cmd` 时：先等 `wait_seconds`（默认 60），跑命令，失败隔 `interval_seconds`（默认 30）重试，最多重试 `retries` 次（默认 3，一共跑 4 次）。没配命令、远端是 GitHub、本机有 `gh` 时：查这个提交的检查结果（check runs）、提交状态（commit statuses，有的 CI 只报这一套）和部署状态；同一来源的同名检查、同一环境的部署只看最新一次（检查的来源是 CI 应用加检查套件：两个 CI、同一个 CI 的两个工作流里都叫 build 的检查各算各的，一个失败就不通过）；提交状态是 failure / error 算不通过，pending 按还在跑处理；部署状态是 inactive（被别的部署替换了）看不出这次成没成，按「无法判断」；还在跑就每 15 秒查一次，满 10 分钟（`--max-poll`）还没完判「无法判断」。有任何一项查询失败（没登录、没权限、网络）时不报通过：查到确定的失败报「不通过」，否则报「无法判断」。都没有：无法判断。
- rollback.py：`--push` 推送时会自己带 `--no-follow-tags`。按给的顺序 `git revert --no-edit`（合并提交加 `-m 1`），提交号要从新到旧给。动手前先查三件事，有一件不对就一个都不动：仓库里有没有没做完的 revert / cherry-pick / merge / rebase（有就报「回滚：失败」，不去中止别人的操作）；提交号是不是都找得到；是不是都在当前分支的历史里。中途撤回失败时只中止自己这一次 revert，已经做好的回滚提交留在本地、在输出里列出来，但不记进审核记录（只撤回一部分，是没审核过的中间状态）。全部撤回成功后，如果内容和某个被撤回提交之前一模一样（平常的上线回滚都是这样），记一个审核单元，起点是那个「之前」的提交：那个状态已经上传过的话，推送不用再审。只撤回了中间一段、内容对不上的不记，输出里会提醒推送前要先审核。带 `--push` 时用守卫上传关的同一套规则查一遍（守卫看不懂会推到哪、有没审核的提交，都不推），再把当前分支推到同名的上游分支；`AGENT_DEV_TEAM_CODEX=off` 时不查，直接 `git push`。只撤回代码，不碰数据库。
- 四个脚本自己出意外错误时，第一行分别是「验收：出错」「审核：出错（不计入失败轮数）」「上线检查：无法判断」「回滚：失败」，不会被当成通过。
- mode.py：状态栏按钮和负责人用。`set` 至少带一个 `--role` / `--auto` / `--status` / `--pool`，改完打印一遍。负责人在派活、验收、审核、合并时用 `--status "<节点>：<任务名>"` 写「现在在做」（状态栏把冒号前当大字、冒号后当小字），一批做完用 `--status ""` 清空；`--pool <N>` 是小任务池攒了几个（攒够 8 个一起派）。

## 审核记录

审核记录按仓库存在 `<git 公共目录>/agent-dev-team/`，所有工作副本共用：`reviewed.jsonl` 是审核单元，`fails-<分支>` 是失败轮数，`last-<分支>.json` 是上一轮没通过的审核（增量复审用）。

一个审核单元 = 一次通过的审核，一行 JSON：`{"tip": 顶端提交号, "fork": 起点提交号, "commits": [起点到顶端这一段的全部提交号], "at": 时间}`。起点是基准和分支的分叉点。Codex 看的是从起点到顶端这一整段的最终结果，所以一个单元只证明一件事：起点那个状态没问题的话，顶端那个状态也没问题。它不证明其中某个提交单独上没问题。

守卫的查法：先算出这次要上传的提交（合并是 `HEAD..<分支>`，推送是「远端的那个分支..要推的分支」）。一个提交的状态算通过，只有三种情况：

1. 它不在这次要上传的提交里（远端或当前分支已经有了）。
2. 它是某个单元的顶端，那个单元的起点也算通过，而且单元这一段的提交都在这次要上传的提交里。
3. 它是两边自动合出来、没夹带改动的合并提交，而且两边都算通过。

通过的提交和它前面的提交可以上传，其余都算没审核，有一个就拦。

- 只带了某个单元的一部分会被拦。例如 A 引入问题、B 撤销，整段审核通过；只合并或只推 A，A 不是任何单元的顶端，不算通过。
- 单元要一环扣一环。例如上面的 A、B 之后再来一个 C 把 B 撤销，然后「从 A 审到 C」（没有改动，通过）：这个单元的起点 A 没通过过，所以不算数，要从主分支把整段重审。
- 审核时的基准太旧也不算数。例如主分支上已经有一个修复 H，任务分支把 H 撤回了，却拿 H 之前的状态当基准去审：Codex 看到的改动里，H 和对它的撤回抵消掉了。这时单元这一段里夹着目标分支上已经有的提交（H），不算数，要拿现在的主分支（或远端的主分支）当基准重审，被拦时提示里给的就是这样的命令。本地主分支落后于远端时审的、再直接推到远端主分支，也是这种情况。
- 审核过的分支上又加了提交：新加的要审。把分支重审一次，或者只审新加的那段（基准写上一次审核的顶端）。
- rebase 之后提交号变了，要重审。
- 正常流程不受影响：审核任务分支 → 合并进主分支（快进或带合并提交都行）→ 推主分支；多个任务分支先后合并再一起推也行。
- 夹带了改动的合并提交（手动解过冲突的、内容和自动合并不一样的）要审。判断不了的（一次合并几个分支、git 太旧不支持 `merge-tree --write-tree`）也按要审算。
- 回滚：撤回之后的内容和某个被撤回提交之前一模一样时，rollback.py 记一个单元，起点是那个「之前」的提交。那个状态早就上传过（平常的上线回滚），推送就不用再审；它本身没通过过，这个单元也不算数。回滚的单元不受上一条「基准太旧」的限制：撤回已经上线的提交本来就是它要做的事。
- 旧格式的 `passed` 文件（一行一个提交号）已经作废，不读也不写，留着不出错；以前通过的提交要重新审核，被拦时提示里会说明。`reviewed.jsonl` 里读不懂的行（包括没有起点的）跳过，不算通过。

## 守卫怎么判

- 普通对话、守卫关了：全部放行。
- 子代理、对接窗口：命令里可能有上传动作就拦。所以它们要跟上主分支或解决合并冲突，只能用 `git rebase`。这一关靠拆命令来认，防的是手误，不防刻意构造的绕过（见下面「防什么、不防什么」）。
- 负责人：
  1. 编辑工具改项目根目录（git 仓库根；不在仓库里就是当前目录）里的文件 → 拦。项目外的文件放行。
  2. 命令行只拦写的动作：重定向写文件（写到 `/dev/null`、`/dev/stdout`、`/dev/stderr`、`/dev/tty` 和 `2>&1` 这类不算）；`rm` `mv` `cp` `tee` `touch` `truncate` `dd` `patch` `install` `ln` `chmod` `chown`；`sed -i` / `perl -i`；`git commit` `add` `checkout` `switch` `reset` `restore` `rebase` `cherry-pick` `stash` `apply` `am` `clean` `rm` `mv`；`find -delete / -exec / -execdir`。拆不开的命令（引号或括号没闭合、一层套一层套得太深）也拦，请改写。这部分是护栏，不是安全边界。
  3. 上传关：见下面。它不靠拆命令。
  4. 半自动：有远端时拦在主分支上 `git merge <分支>`、拦推到主分支（推送看推到的那个远端自己的主分支：origin 的是 main、upstream 的是 master 时，推到 upstream 的 master 也拦）；`gh pr merge` 和 `gh api` 的写操作一律拦，PR 由用户自己点合并。查不出主分支是哪个时也拦。
- 普通命令遇到守卫自己出错一律放行。负责人的上传命令遇到守卫出错、git 出错、查不出要上传什么，一律拦。
- 守卫自己限时 20 秒（钩子的超时是 30 秒，钩子超时会被当成放行）。命令一读进来就登记，超时的时候（哪怕还在认角色），命令原文里出现 `push` / `merge` 这类词或者 `gh` 就拦，其余放行。

上传动作指：`git push`、`git merge`、`gh pr create`、`gh pr merge`、`gh api` 的写操作。

### 防什么、不防什么

- 负责人的上传关不靠拆命令，刻意构造的写法也拦。判断「是不是可能上传」只看命令原文里有没有 `push`、`merge`、`send-pack`、`pr create` 这些词；有，整条命令就必须通过一个按字符的严格检查，只能是一条最简单的上传命令。前几轮的教训是：守卫去拆 `$( )`、引号、heredoc，总有和真 shell 对不上的地方，对不上一处，后面的命令就被藏起来了。所以负责人这边干脆不拆。
- 子代理和对接窗口的禁推防的是手误：它们本来就能改文件、能跑任何程序，写个脚本、用 `python3 -c`、设个别名都能把提交推上去，守卫挡不住。这一关靠拆命令来认上传动作，常见写法和很多冷门写法都认得出（`tests/test_shell_diff.py` 拿真的 bash / zsh 对照过），但不保证拆得和真 shell 完全一样。真正的关口是负责人这边：子代理推不上去的东西，最后都要经过负责人的合并和推送。
- 两边都不防的见「已知限制」。

### 负责人的上传关

**第一步：只看命令原文。** 原文里，或者去掉引号和反斜杠之后的原文里（`pu''sh`、`pu\sh`、`$'pu\x73h'`），能找到 `push`、`merge`、`send-pack`、`pr create`，就算可能上传。拆命令的结果只用来多拦几种原文里没有这些词的写法（`gh api` 的写操作、`git $x`），从不用来放行。

**第二步：按字符的严格检查。** 不拆任何嵌套，整条命令只能是「一条最简单的命令」：

- 单引号里什么字都行（PR 正文可以换行）。
- 双引号里不能有 `$`、反引号、反斜杠、`!`。
- 引号外面只能是普通的字和空格。`$` `` ` `` `;` `&` `|` `(` `)` `<` `>` `\` `#` `{` `}` `*` `?` `[` `]`、换行都不行，词的开头也不能是 `=`。所以 `cd x && git push`、`git push | tail`、`git push 2>&1`、`git push origin $BRANCH`、`--body "$(cat <<EOF ...)"` 都拦，提示「上传命令请单独运行，写成最简单的形式」。

通过了这个检查，shell 不会再对命令做任何展开，里面也不可能再藏着第二条命令：守卫看到的词就是 git 拿到的参数。唯一的例外是词开头没加引号的 `~`（shell 会展开），所以 `git -C` 的路径里有 `~` 一律拦；`-C` 的路径守卫不自己算，原样交给 `git -C <路径> rev-parse --show-toplevel`，以 git 认的仓库为准（符号链接后面跟 `..` 时两种算法不一样），git 报错就拦。

**第三步：只认这几种上传写法**，前面最多加 `rtk` / `rtk proxy`：

- `git [-C <路径>] merge ...`：只认 `git merge [--no-ff] [--ff-only] [--no-edit] <一个分支> [-m <说明>]`，以及 `git merge --abort` / `--quit`（直接放行）。`--continue`、`-s`、`-X`、`--squash`、`--no-commit`、一次合并几个分支、分支名带 `~` `^` 的、`FETCH_HEAD` 这类特殊名字都拦。要合并的提交 = `HEAD..<分支>`。
- `git [-C <路径>] push ...`：只认 `git push`、`git push <远端>`、`git push <远端> <分支>`、`git push <远端> <本地分支>:<远端分支>`，可以加 `-u`、`--no-follow-tags`。
  - 远端必须是仓库里配置好的远端名，不能是网址或路径。要推的必须是本地分支或 `HEAD`。
  - `:`、`:<分支>`、`+`、几个分支一起推、`--all`、`--mirror`、`--tags`、`--branches`、`--delete`、推标签，一律拦。远端分支名以 `heads/`、`tags/`、`remotes/`、`refs/` 开头的也拦（`feat:heads/main` 其实就是推到 main）。
  - `--force`、`--force-with-lease`、`-f` 一律拦，负责人不强推。
  - 不带分支的写法，要求当前分支的上游就是同名的远端分支，否则拦，提示改用 `git push -u <远端> <分支>`。
  - 没写明「本地:远端」时，推什么、推到哪要看仓库配置。仓库配置了 `push.default`（`simple`、`current` 以外的值）、`remote.<名>.push`、`remote.<名>.mirror`、`pushRemote`、`remote.pushDefault` 时拦，提示改用两边都写明的写法。
  - 仓库配置了 `push.followTags`（为真）时，推分支会顺带推上标签：所有写法（包括两边都写明的）都拦，提示加 `--no-follow-tags` 或关掉这个配置。
  - 要上传的提交 = 「远端的那个分支..要推的分支」。远端还没有这个分支时，从远端的主分支（远端的 HEAD、main、master）算起。
- `gh pr create ...`：只认 `--head`、`--base`、`--title`、`--body`、`--fill`、`--draft` 这类选项；`-R` / `--repo`、`--web`、多余的参数都拦。查的是本地的 head 分支（不写就是当前分支），要上传的提交 = 「远端的 base 分支..head 分支」。
- `gh pr merge` 和 `gh api` 的写操作：负责人一律拦，守卫查不出会上传什么。全自动用 `git merge` 再 `git push`。
- 带着这些词、但确定不是上传的三种放行（同样要先通过第二步的检查）：git 的只读子命令（`git merge-base`、`git log --merges`、`git branch --merged`、`git worktree add -b feat/push-x ...`，子命令限 `log` `diff` `show` `status` `branch` `worktree` `merge-base` `rev-parse` `rev-list` `blame` `describe` `shortlog` `reflog` `revert` `ls-files` `for-each-ref` `show-ref` `tag`）；`gh pr view / list / checks / status / diff`；插件自己的脚本（`python3 <review.py 的路径> --branch feat/merge-x`，`verify.py` 的 `--cmd` 里带这些词的不算）。
- 其余带着这些词的命令一律拦：`grep "git push" 文件`、`make push`、`./merge.sh`、`python3 -c "...push..."` 都在内。
- 查不了就拦：不在 git 仓库里、仓库没有远端却要推送、远端还没有任何分支（第一次推送，请用户自己推）、找不到分支、git 出错。
- 上面都过了，再按「审核记录」的查法查要上传的提交。有没审核的就拦，提示里给出要跑的审核命令。守卫自己不跑 Codex。

### 子代理和对接窗口：靠拆命令认上传动作

- 把命令按 `;` `&&` `||` `|` `&`、换行、括号拆成一段段。`$( )`、反引号、`bash` / `sh` / `zsh -c "..."`、`eval "..."`、`trap "..."`、`alias 名字="..."`、喂给 shell 的 heredoc 和 `<<<`、没加引号的 heredoc 正文里的 `$( )`，里面的命令也拆开查。
- 一段命令里，`git` 或 `gh`（不分大小写）不管出现在第几个词，后面跟着上传的子命令就算。所以不靠包装器名单：`env git push`、`timeout 30 git push`、`rtk proxy git push`、没见过的包装器都认得出。也不去记 git、gh、shell 的哪些选项带值：选项后面那个词可能是选项的值，也可能就是子命令（或脚本），两种都算。`git send-pack`、`git subtree push`、`git lfs push`、`gh pr new`、`gh repo create --push` 也算。代价是 `echo git push`、`git -C push status` 也算；`grep "git push" f` 这种加了引号的不算。
- `gh api` 只有明显只读的才放：没指定方法或 `-X GET`，加上 `--jq`、`-H`、`--paginate` 这类只影响输出的选项。带 `-f` / `-F` 而没明说 GET、别的方法、`graphql`、认不出的选项，都按写算。
- 看不懂的结构，加上命令文字里出现 `push`、`merge`、`send-pack`、`pr create` 这些词，按「有」算。看不懂的结构是：拆不开（引号括号没闭合、套得太深）；命令名是变量、命令替换、通配符或花括号展开（`$GIT push`、`{git,push}`）；shell 或 `source` 从标准输入读命令而守卫看不到内容（`... | bash`）；git / gh 的子命令由 `xargs`、`find -exec` 拼出来；命令替换里拿不准的写法（`case` 语句、带括号或引号的注释、不寻常的 `<<`）。`git` 的子命令是变量（`git $x`）或带着临时别名（`git -c alias.p=push p`）时，不管有没有这些词都算。
- 拆法照着真的 bash 和 zsh 核对过一批写法（嵌套双引号里的 `$( )`、`((命令); x)` 不是算术、反引号里再套反引号、`$'...'` 里的转义、zsh 的 `{命令}` 和 `=git`、括号里开的 heredoc 等）。这不等于拆得和真 shell 完全一样。

## 开关

- 整个关掉：环境变量 `AGENT_DEV_TEAM=off`，或在项目里建空文件 `.claude/agent-dev-team-off`。
- 只关审核关：环境变量 `AGENT_DEV_TEAM_CODEX=off`。全自动下上传关整个跳过；半自动下只是不查审核记录，上传命令的写法和半自动限制照旧。
- 换审核命令：环境变量 `AGENT_DEV_TEAM_CODEX_CMD`（项目配置的 `codex_cmd` 优先）。

## 项目配置（可选）

`<项目根>/.claude/agent-dev-team.json`，每个键都可以不写：

```json
{
  "default_auto": "full",
  "deploy_check": {"cmd": "curl -fsS https://example.com/health", "wait_seconds": 120, "retries": 5, "interval_seconds": 30},
  "db_backup_cmd": "",
  "codex_cmd": ""
}
```

| 键 | 意思 |
|---|---|
| `default_auto` | 新对话默认全自动（`full`）还是半自动（`semi`）。不写就是全自动 |
| `deploy_check.cmd` | 推送后检查线上的命令，退出码 0 算通过 |
| `deploy_check.wait_seconds` | 推送后先等多少秒再检查，默认 60 |
| `deploy_check.retries` | 检查失败后最多重试几次，默认 3 |
| `deploy_check.interval_seconds` | 每次重试之间隔多少秒，默认 30 |
| `db_backup_cmd` | 动数据库前的备份命令。不配时，动数据库的任务不会自动上线，负责人会先问你 |
| `codex_cmd` | 审核命令。不写就用 `codex exec --sandbox read-only -c model_reasoning_effort=max`，型号跟着本机 Codex 配置走 |

数字写错了（不是数字或是负数）按默认值算。

- Codex 命令行（审核用）。
- `gh`（半自动开 PR、查 GitHub 上线状态用，可选）。
- Notion 和 Slack 连接（任务卡和汇报用）。

## 已知限制

- 守卫是护栏，不是安全边界。负责人的上传关拦的是「命令原文里带着上传字样」的一切写法；下面这些原文里没有这些词，或者根本不走命令行，两边都挡不住：
  - 脚本文件、别的程序里间接上传，而命令原文里没有这些词：`bash deploy.sh`、`make release`、`python3 发版.py`。
  - shell 里早就定义好的别名和函数（比如 oh-my-zsh 的 `gp` 就是 git push），git 和 gh 的别名（`git config alias.p ...` 之后的 `git p`）。
  - 用变量、展开、编码拼出这些词：`a=pu; b=sh; git $a$b` 两边都拦（`git` 的子命令是变量）；`$G $a$b`、`echo <base64> | base64 -d | bash` 拦不住。
  - 绕开 git 和 gh 的上传方式：`curl` 调 GitHub 接口、`hub`、`glab`、`git send-email`、不走命令行的工具（比如 GitHub 的 MCP 工具）。
  - git 自己会去跑的命令：git 钩子、`core.pager` 这类配置里写的命令。
  - 审核记录和远端跟踪分支都在本地的 `.git` 里，能在仓库里跑命令的人都能改：直接写 `reviewed.jsonl`、用假的审核命令跑 review.py（`AGENT_DEV_TEAM_CODEX_CMD`）、`git update-ref refs/remotes/origin/main ...`。
  - 守卫在命令运行前检查。检查之后、真正上传之前，别的窗口挪了分支，守卫看不到。
  - 合并关只认 `git merge`。`git pull <远端> <分支>`、`git branch -f`、`git update-ref` 这类把提交挪进主分支的不拦。有远端时推送照样查；没有远端的本地仓库就没有第二道关。
  - 负责人的黑名单只拦列出来的命令。
- 子代理和对接窗口的禁推只防手误。除了上面这些，带着上传字样的刻意写法它也可能认不出：`python3 -c "...git push..."`、`watch 'git push'`、`su -c`、`ssh 主机 '...'`、`git rebase --exec`、`PS4='$(...)'; set -x`、zsh 特有的冷门写法，以及任何守卫拆得和真 shell 不一样的写法。同样的命令到了负责人那边会被拦。
- 负责人的上传关是保守判断，下面这些会被误拦：
  - 带着 `push` / `merge` 这些词、又不在放行名单里的只读命令：`grep -rn merge src`、`cat docs/push.md`、`git fetch origin feat/merge-x`、`git log --merges | head`。换个写法，或者派给子代理。分支名、文件名最好别带这些词。
  - 上传命令和别的东西写在一起：`cd x && git push`、`git push | tail`、`git push 2>&1`、`git merge x && git push`。分开单独运行，不加重定向。
  - 合并说明、PR 标题和正文里有 `$`、反引号、反斜杠、`!` 而用了双引号，或者用了 `$(cat <<'EOF' ...)`。写在单引号里；正文里要有单引号的话，用 `--body-file` 先让子代理把正文写成文件。
  - 强推、删远端分支、推标签、第一次推送到空的远端：这些请用户自己做，或者用户先说「普通对话」。
- 子代理和对接窗口这边的误拦：`echo git push` 这种把 git push 当普通词的（加引号就不算）；变量当命令名、shell 从标准输入读命令、命令替换里有 `case` 语句，同一条命令里又出现这些词；`gh api` 用 POST 做的读操作。
- 审核看的是一段提交的最终结果。中间提交的内容（比如加了又删掉的文件）会跟着历史一起上传，Codex 不一定看过。
- 增量复审通过时，Codex 只确认了上一轮的问题、审了上一轮以来的改动，没有把整段从头再看一遍。上一轮全量审时没发现、这次的改动也没碰到的问题，增量复审不会再找出来；要从头审就加 `--full`。
- `gh pr create` 查的是本地的 head 分支，不是远端上那个分支的实际内容。
- 审核员是模型。被审的改动里可以写话去骗它，review.py 只管认整行的结论，管不了 Codex 自己被说服；Codex 在结论后面又原样引用了一行 `VERDICT: PASS` 的话，也会被当成通过。
- 回滚提交不经 Codex 审核就记进审核记录。rollback.py 只保证撤回的是当前分支历史里的提交；撤回哪些由负责人定，撤回一个修复也会把原来的问题带回来。
- 和最初的规格不一样的地方：通过记录从「一行一个提交号」改成了审核单元；负责人的上传关从「拆命令、查不了就放行」改成了「只看原文、按字符检查、看不懂就拦」（第一次推送、不在仓库里都拦）；负责人不能强推、不能用 `gh pr merge`；夹带改动的合并提交要审；黑名单多拦了包装器（`sudo` `env` `timeout` 等）后面的命令和 `bash -c`、`eval`、喂给 shell 的 heredoc 里的命令，多放了重定向到 `/dev/stdout`、`/dev/stderr`、`/dev/tty`。
- 新对话默认是负责人模式，对所有文件夹都生效，不只是 git 项目。不想要时说「普通对话」，或用「开关」关掉。
- 普通对话里开的后台子代理不受守卫限制（规格里没有这条，是后加的）。
- `rollback.py --push` 在脚本里直接推送，不经过守卫的半自动限制，半自动模式下也会直接推主分支（审核记录和推送的写法照样查）。
- 状态栏改对话状态文件时不加锁（它用不了文件锁），和钩子同时改时可能丢一次改动；钩子之间互相加了锁。
- 升级前就开着的旧对话没有 `<session_id>.told`：第一条消息只把当前的角色和模式记下来，不提示。在这条消息之前点过状态栏按钮的话，那一次切换 AI 不知道；之后再切换就正常提示。
- 回滚只能撤回代码，不碰数据库。数据库出问题靠任务里的「改回来」脚本或备份。
