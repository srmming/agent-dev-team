# 清理（交回前精简代码）

目标：同样的功能，更少的代码。每多一行，以后都要有人读、测、修。
只清理这次任务改过的代码。找到就直接改，不只列清单。

## 做法

1. **定范围。** 用 `git diff <主分支>...HEAD --stat` 拿本任务改过的文件清单，只动这些文件。清单外的文件一律不碰，哪怕那里也有可清理的。
2. **先拿基线。** 跑一遍完成标准里的测试，确认现在是绿的。起点就是红的，先交回说明，不要开始清理。
3. **逐类去找**（每一处都要读上下文、grep 调用方，确认真的没人用再动）：
   - 死代码：没人调用的函数、变量、导入，永远走不到的分支，注释掉的旧代码。
   - 重复：几处近似的代码，改一处另一处也得改的，合并成一处。
   - 有现成的：标准库、已装的库、项目里已有的函数能做同样的事，就用现成的（写明路径），不自己写。为几行代码新装依赖不算。
   - 没人用的抽象：只有一个实现的接口或基类，没人传的参数，没人设的配置和选项，为"以后可能要"写的功能。
   - 过度防御：同一个值在内部已经检查过，又在下一层重复检查；永远不会发生的情况写的兜底。
4. **直接删改，分批做。** 每改完一批（一类或几处），跑一次测试。挂了就把这一批撤回（`git checkout -- <文件>`），在汇报里记一笔，继续下一批。
5. **提交。** 全部做完，测试全绿，在当前分支提交，提交信息写"清理：……"。
6. **交回。** 删了多少行（`git diff --stat` 的数字）、动了哪几类、哪些拿不准没动、测试结果。

## 底线（不许删、不许改）

- 输入校验：来自用户、文件、网络的数据的检查。
- 防丢数据的错误处理：写文件、写库、重试、回滚、备份相关的捕获和判断。
- 安全相关的代码：权限、鉴权、转义、密钥、路径限制。
- 对外接口和行为：公开函数的签名、返回值、命令行参数、输出格式、文件格式。
- 测试本身：已有测试只许加行，不删不改原来的行，不加跳过标记。

## 拿不准就不动

- 看不出是否有人在用（反射、动态调用、配置里按名字引用、别的仓库在用）。
- 删了以后行为可能有一点点不一样。
- 为了"更短"要把一个函数拆开或把几个函数硬揉在一起。只在真有重复或真是死代码时才动。
- 只是写法不同、没有更短的，不动。不改命名、不调格式，那是个人口味。

这些写进交回的"没动"清单，一行一条，说明为什么拿不准。
